# Type Inference

Механизм автоматического вывода типов помогает представить код с неявными типами
в общем AST и сгенерировать объявления для языков с явной типизацией. Его результаты
также используются при анализе полей, вызовов и преобразований типов.

Основной класс — [`SimpleTypeInferrer`](../../modules/common/src/main/java/org/vstu/meaningtree/utils/analysis/types/SimpleTypeInferrer.java)
из пакета `org.vstu.meaningtree.utils.analysis.types`. Он реализует локальный
эвристический вывод по форме узлов, известным типам и контексту операций.
Это не полноценный алгоритм Хиндли — Милнера: здесь нет унификации переменных
типов, генерализации и инстанцирования полиморфных схем. Ранее класс назывался
`HindleyMilner`.

## Точки входа и запуск

Основные статические методы `SimpleTypeInferrer`:

- `inference(expression, scope)` возвращает тип выражения и может обновлять
  типы переменных в таблице видимости.
- `inference(node, scope)` и перегрузки для объявлений, операторов и списков узлов
  выполняют обработку ради побочных эффектов: обновления таблицы и типов в AST.
- `inference(expression)` использует новую пустую `ScopeTable`, поэтому не знает
  типов переменных из окружающей программы.
- `chooseGeneralType(first, second)` и `chooseGeneralType(types)` объединяют типы
  по фиксированным эвристическим правилам.
- `backwardVariableTypeSet(expression, scope, type)` распространяет тип внутрь
  выражения на простые идентификаторы.
- `inferenceOperandsTypeByExpressionType(expression)` задаёт тип неизвестных
  операндов некоторых операций.

При разборе [`BodyConstructor`](../../modules/common/src/main/java/org/vstu/meaningtree/languages/BodyConstructor.java)
регистрирует добавляемый узел в таблице видимости и вызывает
`TranslatorContext.processInfer(node)`. Метод `TranslatorContext.inferType(expr)`
возвращает тип выражения с текущей таблицей. Языковые парсеры и генераторы могут
вызывать вывод дополнительно: например, PythonParser — при разборе присваиваний,
JavaViewer — при генерации объявлений переменных.

Вывод не является единственным проходом, который один раз полностью типизирует
готовое дерево. Его результат зависит от доступной таблицы видимости и от того,
какие обработчики были вызваны.

## Области видимости

[`ScopeTable`](../../modules/common/src/main/java/org/vstu/meaningtree/utils/scopes/ScopeTable.java)
управляет текущей областью и хранит области программы. Отдельная область представлена
[`ScopeTableElement`](../../modules/common/src/main/java/org/vstu/meaningtree/utils/scopes/ScopeTableElement.java),
связанной с родительской областью. Эти классы заменили `TypeScope` и `TypedEntities`.
Они хранят типы переменных, декларации и определения; таблица также содержит индексы
типов, членов и перегрузок, используемые другими анализаторами.

Основные операции:

- `enter()` / `leave()` — управление областями при их построении.
- `registerVariable(declaration)` — регистрация объявления переменной.
- `registerDeclaration(name, declaration)` / `registerDefinition(name, definition)` —
  регистрация других объявлений и определений.
- `getVariableType(name)` — поиск типа переменной с учётом видимости и привязок имени.
- `changeVariableType(name, type)` — обновление или создание записи согласно правилам
  связывания присваиваний.
- `inScope(scopeId, action)` / `runInScope(scopeId, action)` — временное переключение
  области с восстановлением текущей области после действия.

Границы областей определяются `ScopePolicy` в `LanguageBehavior`: Java и C++
используют блочную видимость, Python — видимость на уровне определений.
Поэтому Python-блоки `if`, `for` и `while` сами по себе не открывают новую область.
Правила `AssignmentBinding` определяют, изменяет ли присваивание ближайшую видимую
переменную или связывает имя локально. Для Python также поддерживаются перенаправления
имён через `global` и `nonlocal`.

При обработке `CompoundStatement` инферрер использует уже привязанную к телу область
через `runInScope`. Новая область при этом не создаётся. Если привязки нет,
обработка остаётся в текущей области.

Для готового или десериализованного дерева таблицу можно построить отдельно:
`ScopeTableBuilder.build(tree, translator.getLanguageBehavior())`.
Построение таблицы не заменяет вывод типов.

## Типы выражений

### Литералы и коллекции

Числовые литералы дают `IntType` или `FloatType`, логические — `BooleanType`,
строковые и интерполированные строки — `StringType`, символьные — `CharacterType`.
`NullLiteral` даёт `UnknownType`.

Для `ListLiteral`, `SetLiteral`, `UnmodifiableListLiteral` и `ArrayLiteral` сначала
используется известная подсказка типа элемента (`typeHint`). Без неё объединяются
выведенные типы элементов. У `DictionaryLiteral` подсказки и вывод для ключей
и значений независимы; результат — `OrderedDictionaryType`.

У `ArrayLiteral` учитываются вложенные массивы: их базовый тип сохраняется,
а число измерений увеличивается. Для невложенного массива размер задаётся числом
элементов литерала.

**Ограничение:** обработчики коллекционных литералов не принимают внешнюю таблицу
видимости. Каждый элемент анализируется через `inference(expression)` с новой
пустой таблицей. Поэтому без подсказки `[x]` может иметь неизвестный тип элемента,
даже если тип `x` известен в окружающей области. Пустая коллекция без подсказки
также получает неизвестный тип элемента.

### Слияние типов: `chooseGeneralType`

Правила применяются в следующем порядке:

| Типы | Результат |
|---|---|
| Хотя бы один `UnknownType` | `UnknownType` |
| Два числовых типа, хотя бы один float | `FloatType` с максимальной разрядностью |
| Два символьных типа | `CharacterType` с максимальной разрядностью |
| Остальные пары числовых типов | `IntType` с максимальной разрядностью |
| Хотя бы один строковый тип, оба типа известны | `StringType` |
| Два логических типа | `BooleanType` |
| Два массива с одинаковым числом измерений | Массив с общим типом элементов; если он неизвестен, весь результат — `UnknownType` |
| Другие равные типы | Свежая копия типа |
| Остальные сочетания | `UnknownType` |

Для массива, полученного слиянием, сохраняется число измерений, но не конкретные
размеры исходных массивов. Пустой список типов даёт `UnknownType`.

Это фиксированная стратегия инферрера. Она не параметризуется исходным языком
и не реализует полностью правила продвижения числовых типов, знаковости
или строковой конкатенации Java/C++/Python.

### Бинарные выражения

1. Выводятся типы левого и правого операндов.
2. Если оба неизвестны, для сравнения предполагается `FloatType`, для логических
   AND/OR — `BooleanType`, для `DivOp` — `FloatType`. Для остальных операций
   предположение может остаться неизвестным.
3. Если известен только один операнд, его тип распространяется на неизвестный
   через `backwardVariableTypeSet`.
4. Сравнения и `InstanceOfOp` возвращают `BooleanType`.
5. `DivOp` возвращает общий числовой тип, если после уточнения оба операнда
   числовые и ни один не float; в остальных случаях — `FloatType`.
6. Для остальных бинарных операций результат определяется `chooseGeneralType`.
   На простые идентификаторы операндов также распространяется общий тип.

Правило деления — компромисс: `DivOp` сам по себе не содержит контекста исходного
языка. Известные целочисленные операнды сохраняют целочисленный результат,
что соответствует C-подобному делению, но не Python-оператору `/`.

### Унарные и другие выражения

`NotOp` возвращает `BooleanType` и распространяет его на операнд.
Для инкремента/декремента, унарных плюса/минуса, инверсии и разыменования
известный тип операнда возвращается без дополнительного преобразования.
Если операнд неизвестен, используются следующие предположения:

| Операция | Предполагаемый тип |
|---|---|
| `InversionOp` | `IntType` |
| `PointerUnpackOp` | `PointerType(UnknownType)` |
| Инкремент/декремент, унарные плюс/минус | `FloatType` |

Эти правила являются эвристиками; в частности, обработка разыменования не является
полным выводом типа значения по типу указателя.

Другие поддержанные случаи:

- `SimpleIdentifier` — тип из таблицы, либо `UnknownType`.
- `ParenthesizedExpression` — тип внутреннего выражения.
- `TernaryOperator` — общий тип двух ветвей; условие также анализируется.
- `CompoundComparison` — анализ сравнений и результат `BooleanType`.
- `Range` — анализ `start`, `stop`, `step`; тип самого диапазона остаётся неизвестным.
- `CastTypeExpression` — свежая копия явно заданного типа приведения.
- `ConstructorCall` — свежая копия типа владельца.
- `FunctionCall` с простым именем — возвращаемый тип функции, найденной по имени
  в текущей или родительской области.

При выводе типа `FunctionCall` аргументы не обходятся и ссылка
`getResolvedDeclaration()` не используется. Поиск через
`ScopeTableElement.getFunctionReturnType(name)` выбирает последнюю подходящую
декларацию в ближайшей области. Он не учитывает типы аргументов или получателя
метода, поэтому может расходиться с результатом отдельного разрешения перегрузки.

## Обратное распространение типов

`backwardVariableTypeSet(expr, scope, type)` обходит выражения очередью и обновляет
простые идентификаторы. Он спускается только в дочерние узлы, являющиеся выражениями,
а не напрямую в объявления, типы и тела лямбд.

Обновление выполняется, когда тип переменной отсутствует или неизвестен,
а также при повышении `IntType` до `FloatType`. Другие известные типы не заменяются
произвольным новым типом. Это частичное уточнение, а не универсальная унификация
или доказательство корректности операции.

## Объявления, присваивания и тела

Если тип `VariableDeclaration` известен, он сохраняется и регистрируется в таблице;
инициализаторы деклараторов всё равно анализируются. При неизвестном объявленном
типе объединяются доступные типы переменных из таблицы либо типы их инициализаторов.

`DeclarationArgument` использует явно заданный тип, иначе тип значения по умолчанию,
иначе `UnknownType`. Неизвестный тип аргумента не затирает уже известный тип в таблице.
Однако это не означает, что параметры любой функции автоматически доступны всем
потребителям инферрера: их регистрация зависит от пути построения таблицы.

Поддерживаются разделённые объявления, цепочки и множественные присваивания.
Обработка распаковки ограничена посещением значения и имён; общего вывода типов
элементов из произвольного контейнера нет.

Обычный `AssignmentExpression` анализируется через временный
`AddOp(lvalue, rvalue)`, независимо от вида augmented operator. Поэтому его результат
нельзя считать полной реализацией семантики всех составных присваиваний.

Инферрер обрабатывает `IfStatement`, `SwitchStatement` и узлы с телом
через `HasBodyStatement`. У циклов анализируются условия, инициализаторы, шаги
или перебираемые выражения. Заголовки `GeneralForLoop`, `RangeForLoop` и `ForEachLoop`
обрабатываются в привязанной области тела; условия ветвей и while — во внешней области.
Обход foreach сам по себе не выводит тип элемента из типа контейнера.

### Объявленный тип и `realType`

[`HasComputedType`](../../modules/common/src/main/java/org/vstu/meaningtree/nodes/interfaces/HasComputedType.java)
реализован у `VariableDeclarator`, `AssignmentExpression`, `AssignmentStatement`
и `ChainedAssignmentStatement`. Их `realType` хранит вычисленный тип инициализатора
или правой части присваивания, а не объявленный тип переменной.

Например, у `double x = 1` объявленный тип — `FloatType`, а тип целочисленного
инициализатора — `IntType`. Пока вывод не выполнен или не дал ответа,
`realType` остаётся `UnknownType`. В JSON это поле называется `real_type`.

`realType` не является поточным типом переменной в каждой точке программы.
При его обновлении тип клонируется с сохранением remapping; эквивалентный тип
не заменяется без необходимости, чтобы повторный вывод не менял идентификаторы узлов.

## Связанные проходы анализа

После построения дерева парсер запускает
[`AnalysisPipeline`](../../modules/common/src/main/java/org/vstu/meaningtree/utils/analysis/AnalysisPipeline.java).
В части анализа типов важны следующие отдельные стадии:

- `SymbolResolver` добавляет или уточняет поля экземпляра по обычным присваиваниям
  `self.x = value` / `this.x = value` в нестатических методах.
- `OverloadIndexer` индексирует члены типов и группы перегрузок.
- `OverloadCallResolver` связывает вызовы с декларациями, учитывая видимость,
  получателя, аргументы и языковые правила перегрузок и преобразований.
  Неоднозначные вызовы остаются несвязанными. Наличие этой связи пока не гарантирует,
  что `SimpleTypeInferrer` использует возвращаемый тип выбранной декларации.
- `TypeConversionAnalyzer` проверяет явные и неявные преобразования в местах передачи
  значений. Правила уточняются для Java, Python и C++; результат — `COMPATIBLE`,
  `INCOMPATIBLE` или `UNKNOWN`. Этот анализ отличается от `chooseGeneralType`.

Конвейер также содержит другие проходы, например оценку значений выражений
и числа итераций циклов. Он не запускает самостоятельный полный проход
`SimpleTypeInferrer` по всему дереву; отдельные стадии обращаются к нему по мере надобности.
`skipOptimizations` отключает регистрацию общего конвейера постанализа,
но не все обращения к выводу при построении тела.

У C/C++ есть отдельный ранний проход
[`CStringTypeInferrer`](../../modules/languages/cpp/src/main/java/org/vstu/meaningtree/utils/analysis/types/CStringTypeInferrer.java),
включаемый параметром `preferCharArrayAsString` (по умолчанию `true`). Он распознаёт
строковое использование `char*` и одномерных `char[]`, заменяет их тип на `StringType`
и распространяет признак по присваиваниям. Признаками служат строковые инициализаторы,
массивы символов с завершающим нулём, известные строковые библиотечные функции
и распознанные узлы строкового ввода-вывода. Ёмкость массива сохраняется.
`char**`, многомерные массивы, const самого указателя и буферы без строковых признаков
не преобразуются. Форматные строки `%s` этот проход не анализирует.

## Ограничения

- Поддержка определяется конкретными обработчиками. Необработанные выражения дают
  `UnknownType`; некоторые неподдержанные декларации могут вызвать исключение.
  Поэтому нельзя обещать полный глубокий анализ произвольного AST.
- Нет общего вывода возвращаемого типа функции по её телу, полиморфных схем
  и анализа потока данных с объединением состояний всех ветвей.
- Неизвестный тип поглощает известный при `chooseGeneralType`, поэтому объединение
  не всегда означает постепенное уточнение.
- Типы коллекционных литералов без подсказок не учитывают внешнюю область видимости.
- Разрешение перегрузки и вычисление типа вызова пока используют разные пути.
- Правила операций являются эвристическими и не заменяют полную проверку типов
  исходного языка или проверку корректности сгенерированного кода.
